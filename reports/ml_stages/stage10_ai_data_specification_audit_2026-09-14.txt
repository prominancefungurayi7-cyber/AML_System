4. STRUCTURING FEATURE AUDIT
FAIL — Required count of 6 is not specified or frozen. The Stage 24 candidate
path contains three direct structuring fields: amount_near_threshold_flag
(current amount in 8,500–9,999), same_day_cumulative_amount (historical same-day
total plus current amount), and structuring_pattern_score (prior same-day
near-threshold count / 3 capped at 1). All use transaction amount/timestamp;
the code filters history strictly before current time, so each is prediction-time
safe in that extractor. They are rule-like threshold features and have potential
rule-concept leakage, though not target-field leakage by themselves.

Other frequency/velocity fields could support structuring, but no approved list
assigns them to this category. Do not infer a sixth feature or silently recategorise.

5. WALLET/TRANSACTION NETWORK FEATURE AUDIT
FAIL — Required count of 10 is not specified or frozen. Existing wallet-level
relationship measures include is_new_recipient, unique_recipients_7d,
counterparty_change_score_7d, recurring_pattern_score and rapid_transfer_count.
They derive from prior sender/receiver history. They are not a documented
10-feature network design, do not establish multi-wallet graph features, and do
not use shared-agent relationships in the ML matrix.

6. AGENT FEATURE AUDIT
FAIL / BLOCKER — Required count: 14. Found in ML input: 0.
agents.py and transaction_simulation.py model agents and agent_id exists in the
database schema/simulator. Neither the active frozen 18 features nor the Stage
24 feature headers contain agent_id or any agent aggregate. No agent historical
feature definitions, agent-level split protocol, or agent-population design was
found. Agent identity is not currently an ML input (good), but required agent
behaviour detection and isolation cannot be audited or supported.

7. TARGET / GROUND-TRUTH AUDIT
FAIL / BLOCKER — The approved target must be binary (0 normal, 1 suspicious
pattern). The frozen Stage 16B path trains three labels: normal, suspicious and
super_suspicious. The Stage 24 ground-truth data uses the same multi-class labels.

PASS (limited) — Stage 11/24 ground-truth JSON associates labels with generated
scenario metadata (scenario_id, scenario_category, aml_typologies), rather than
reading risk_score or rule output in the Stage 16B trainer.

BLOCKER — ai_core.py retains map_risk_to_ai_label(risk_level, risk_score), and
train_ai_model calls it. Earlier baseline reports explicitly identify this as
rule/risk-derived label leakage. Therefore the operational AI path cannot be
certified as having an independent target.

8. TEMPORAL-SAFETY AUDIT
PASS (limited to Stage 16B extractor) — each of the 18 frozen inputs is current
transaction data or filters same-sender history with timestamp < current timestamp.
PASS (limited to Stage 24 extractor) — it sorts sender history and uses records
strictly earlier than the current timestamp for rolling measures.
WARNING — equal timestamps have no defined event ordering and are excluded rather
than deterministically sequenced. The generator initially creates transactions in
random timestamp order and recalculates only some raw baseline fields after
sorting; the downstream extractor recomputes many measures, but the complete
raw-data temporal contract remains undocumented.
FAIL — temporal safety cannot be certified for a non-existent frozen 30-feature
design, and no agent historical features exist to audit.

9. CUSTOMER / WALLET ISOLATION AUDIT
PASS (historical Stage 16B) — ml_stage12_primary_split.json documents an 80/20
customer-level holdout with 160 train, 40 test and zero customer overlap.
PASS (Stage 24 code intent) — ml_stage24_populations.py splits sender_account
sets before creating train/dev/test frames; ml_stage24_independent_generator.py
uses a distinct seed and customer_id_offset.
WARNING — no approved future 100,000-wallet population/split specification exists.
The methodology does not document treatment of a receiver wallet that also occurs
in another group, related wallets, or cross-group transaction edges. This must be
resolved before final data generation.

10. AGENT ISOLATION AUDIT
FAIL / BLOCKER — No agent feature matrix, agent-level group split, agent overlap
check, or independent-agent evaluation is implemented. The current ML datasets
do not carry agent data, so the model cannot evaluate agent generalisation and
cannot demonstrate that it is not memorising agent identity.

11. LEAKAGE AND NON-ML FIELD EXCLUSION AUDIT
BLOCKER — Stage 24 save_features excludes only transaction_id, sender_account and
ground_truth_label. Its result reports 32 fields, not the required 30. The future
matrix contract does not explicitly exclude customer_id, wallet_id, agent_id,
receiver_account, scenario metadata, provenance, rule outputs, risk values and
investigation outcomes.
WARNING — Stage 24's ground_truth_label is added to a dataframe before feature
selection; the quality audit correctly flags it as label-derived when it sees it.
The downstream population writer does remove it, but the pipeline contract is
fragile and not an auditable allow-list.
BLOCKER — map_risk_to_ai_label in ai_core.py is a direct risk/rule-derived target
mechanism on the active AI path.
WARNING — Stage 24 includes cross-border/high-risk-country fields and scenarios;
these are outside the specified Stage 10 core scope unless separately approved.
